# Тестирование rustos

Ядро работает без стандартной библиотеки (`no_std`), поэтому встроенный тестовый
фреймворк Rust (крейт `test`) недоступен. Тесты собираются в отдельные загрузочные
образы и запускаются внутри QEMU; результат передаётся наружу через код выхода
QEMU и последовательный порт.

## Как запустить

```sh
make test                      # все тесты (то же, что cargo test)
cargo test --lib               # только unit-тесты из src/
cargo test --test basic_boot   # один интеграционный тест
```

Нужны `bootimage` (`cargo install bootimage`) и `qemu-system-x86_64` в `PATH`.

## Как это устроено

```
cargo test ──► сборка тестового образа ──► bootimage runner ──► QEMU
                                                                  │
      serial (COM1, 0x3F8) ──► stdout терминала ◄─────────────────┤
      isa-debug-exit (порт 0xF4) ──► код выхода QEMU ◄────────────┘
```

- **Кастомный тест-раннер.** `#![feature(custom_test_frameworks)]` собирает все
  функции с атрибутом `#[test_case]` и передаёт их в `rustos::test_runner`
  (`src/lib.rs`). Раннер выполняет их по очереди и печатает `имя...\t[ok]`.
- **Вывод.** Тесты пишут в последовательный порт (`serial_print!` / `serial_println!`),
  QEMU перенаправляет его в stdout (`-serial stdio`). VGA-вывод (`println!`) в
  тестах тоже работает, но его не видно, потому что окно QEMU отключено (`-display none`).
- **Результат.** Раннер записывает `QemuExitCode` в порт `0xF4` устройства
  `isa-debug-exit`. QEMU завершается с кодом `(value << 1) | 1`:
  - `Success = 0x10` → код 33, который указан в `test-success-exit-code`, bootimage считает это успехом;
  - `Failed = 0x11` → код 35, тест считается упавшим.
- **Паника.** В тестовой сборке `#[panic_handler]` вызывает
  `test_panic_handler`: печатает `[failed]` с сообщением паники и выходит с `Failed`.
  Поэтому любой упавший `assert!` роняет весь тестовый образ: тесты после
  него уже не выполняются.
- **Зависание.** Если тест завис (например, из-за deadlock), bootimage убьёт QEMU
  через `test-timeout = 300` секунд и засчитает провал.

Настройки QEMU для тестов лежат в `[package.metadata.bootimage]` в `Cargo.toml`.

## Виды тестов

| Вид | Где лежит | Когда использовать |
|---|---|---|
| Unit-тесты | `src/<модуль>/tests.rs` | Проверка отдельного модуля, в том числе его приватных полей и функций |
| Интеграционные | `tests/<имя>.rs` с тест-раннером | Проверка поведения в «чистом» окружении: отдельный образ, собственный `_start` |
| Тесты на панику | `tests/<имя>.rs` с `harness = false` | Проверка того, что код **должен** паниковать |

### Unit-тесты (`src/<модуль>/tests.rs`)

Тесты не смешиваются с кодом: у каждого модуля они лежат в отдельном файле.

```
src/
├── lib.rs                ← в конце: #[cfg(test)] mod tests;
├── tests.rs              ← тесты lib.rs
├── drivers.rs            ← только объявления подмодулей, своих тестов нет
├── drivers/
│   ├── vga.rs            ← в конце: #[cfg(test)] mod tests;
│   ├── vga/
│   │   └── tests.rs      ← тесты drivers::vga
│   ├── serial.rs
│   └── serial/
│       └── tests.rs
├── mm.rs
└── mm/
    ├── allocator.rs
    └── allocator/
        ├── tests.rs      ← тесты mm::allocator
        ├── bump.rs       ← в конце: #[cfg(test)] mod tests;
        └── bump/
            └── tests.rs  ← тесты mm::allocator::bump (так же linked_list, fixed_size_block)
```

`tests` — дочерний модуль тестируемого модуля, поэтому через `use super::*;`
ему доступны **приватные** типы, поля и функции (например, `ColorCode(0x1e)` или
`writer.column_position`). Из `tests/` их было бы не видно. Благодаря
`#[cfg(test)]` файл компилируется только при `cargo test` и в образ ядра не попадает.

Строку `mod tests;` ставим **в конец** файла модуля, после объявлений
`macro_rules!`: макросы (`println!`, `serial_println!`) видны только в коде,
который идёт после их определения.

Чтобы покрыть тестами новый модуль `foo`:

1. добавить в конец `src/foo.rs` строки `#[cfg(test)]` и `mod tests;`;
2. создать `src/foo/tests.rs`, начинающийся с `use super::*;`;
3. писать тесты с атрибутом `#[test_case]`.

Все unit-тесты библиотеки собираются в один образ, поэтому у них общее
глобальное состояние (`WRITER`, `SERIAL1`).

Сейчас покрыто:

- `drivers::vga`: кодирование цвета, раскладка структур в памяти (должна совпадать
  с текстовым VGA-буфером), вывод строки, перенос длинной строки, сброс колонки
  после `\n`, прокрутка экрана, замена не-ASCII байтов на `■` (`0xfe`), цвет
  записанных символов, «стресс» из 200 строк;
- `drivers::serial`: вывод через последовательный порт с форматированием;
- `console`: дублирование в serial по умолчанию выключено (serial занят отчётом
  тестов) и включается/выключается; `print!`/`println!` пишут на экран, в том
  числе при включённом serial, `print!` продолжает строку, аргументы форматируются;
- `time`: `tick` увеличивает счётчик ровно на один, без `tick` счётчик не меняется;
- `lib`: соответствие `QemuExitCode::Success` значению `test-success-exit-code`;
- `arch::x86_64::interrupts`: в IDT зарегистрированы обработчики breakpoint, double fault,
  page fault, таймера, клавиатуры и COM1, у остальных исключений и линий IRQ
  обработчиков нет; смещения PIC идут сразу после 32 исключений CPU, а
  `InterruptIndex` совпадает с линиями IRQ; маски PIC включают ровно линии
  с обработчиками (0, 1, 4) и каскад (2);
- `arch::x86_64::gdt`: в TSS задан стек для double fault (IST), остальные записи IST пустые;
  раскладка GDT (код ядра, TSS) и уровень привилегий селекторов (ring 0);
- `mm::paging`: `BootInfoFrameAllocator` на выдуманной карте памяти: выдаёт фреймы
  только из `Usable`-регионов, по порядку и с шагом 4 KiB, возвращает `None`,
  когда фреймы кончились;
- `mm::allocator`: адрес и размер кучи (выровнены по страницам, адрес канонический),
  `Dummy` всегда возвращает null, `align_up`, `Locked`;
- `mm::allocator::bump`: аллокации идут подряд с учётом выравнивания, null при
  нехватке памяти, память переиспользуется только после освобождения всех аллокаций;
- `mm::allocator::linked_list`: `size_align` подгоняет layout под `ListNode`, аллокация
  делит регион, освобождённый регион попадает в начало списка и переиспользуется,
  слишком маленькие регионы и остатки меньше `ListNode` пропускаются;
- `mm::allocator::fixed_size_block`: выбор списка по размеру и выравниванию
  (`list_index`), блоки выровнены по своему размеру, освобождённые блоки
  выдаются повторно (LIFO), списки разных размеров не смешиваются, большие
  аллокации идут через fallback-аллокатор;
- `task`: `TaskId` уникальные и возрастают. Задачи и executor'ы проверяются в
  интеграционных тестах;
- `task::queue`: без читателя `push` возвращает `Uninit`, в полную очередь -
  `Full`; поток отдаёт элементы по порядку, на пустой очереди - `Pending`, а не
  конец; `push` будит только ждущего читателя, неудачный `push` не будит;
  очередь работает с любым типом элементов;
- `tty::key`: `from_control` разбирает Enter (`\n`, `\r`), Backspace (BS и DEL),
  Tab и Ctrl + буква, остальные управляющие символы отбрасывает;
- `tty::keyboard`: `KeyboardDecoder` на скан-кодах набора 1: буквы, цифры, пробел,
  Shift (заглавные и символы), отпускание и одиночный Shift ничего не дают,
  Enter/Backspace/Tab, Esc игнорируется, Ctrl + буква, стрелки, Home, End и
  Delete с префиксом `0xE0`;
- `tty::serial`: `SerialDecoder`: печатные символы, Enter как `\r`, `\n` и одно
  нажатие на `\r\n`, Backspace (DEL и BS), Tab, Ctrl + буква, стрелки, Home/End/Delete
  в формах `ESC [ X`, `ESC [ N ~` и `ESC O X`, стрелка с модификатором, неизвестные
  и испорченные последовательности пропускаются без поломки декодера, огромный
  параметр не переполняется, UTF-8 из 2, 3 и 4 байтов, оборванные, лишние,
  недопустимые и «слишком длинные» байты UTF-8 отбрасываются.

Куча в unit-тестах инициализирована в `test_kernel_main` (`src/lib.rs`) так же,
как в `kernel_main`, поэтому `Box`, `Vec`, `String` и очереди `ArrayQueue`
работают. Аллокаторы при этом всё равно проверяются напрямую через
`GlobalAlloc::alloc`/`dealloc` на статическом массиве: так видно их внутреннее
состояние, и тест не зависит от того, что в куче уже лежит.

Таблицы IDT, GDT и TSS в unit-тестах только строятся, но не загружаются в CPU
(см. правило 4). По той же причине тестовая точка входа `test_kernel_main`
в `src/lib.rs` **не**
вызывает `rustos::init()`: в unit-тестах прерывания выключены.

### Интеграционные тесты (`tests/`)

Каждый файл собирается в **отдельный** загрузочный образ со своим `_start`. Это
позволяет проверить, что код работает сразу после загрузки, без инициализации
из `main.rs`, и изолировать тесты, которые меняют глобальное состояние CPU
(прерывания, GDT, таблицы страниц, куча и т.д.).

- `basic_boot.rs`: VGA- и serial-вывод доступны сразу после загрузки.
- `interrupts.rs`: после `rustos::init()` (загрузка GDT, TSS и IDT) исключение breakpoint
  (`int3`) обрабатывается, в том числе многократно, и выполнение продолжается;
  загружена GDT ядра, а `CS` указывает на сегмент кода ядра; в PIC записаны маски
  `PIC_1_MASK`/`PIC_2_MASK`; прерывания включены,
  прерывания таймера приходят и увеличивают `time::ticks`, обработчик таймера
  ничего не печатает, а `println!` не попадает в deadlock с обработчиками прерываний.
- `keyboard.rs`: скан-коды доходят до потока `drivers::keyboard::scancodes()`
  без изменений и по порядку (в том числе отпускания); пустой поток - `Pending`;
  нажатие будит поток, а прерывания таймера - нет. Нажатия эмулируются
  `common::press_key`. Поток опрашивается вручную, без executor'а, с waker'ом,
  который запоминает пробуждение. Если обработчик не сработает, CPU уйдёт в
  triple fault, и тест упадёт (QEMU запускается с `-no-reboot`).
- `serial_input.rs`: байты из терминала доходят до потока `drivers::serial::input()`
  по порядку и без изменений (escape-последовательности, UTF-8), в том числе
  полный FIFO за раз и длинный текст по частям; пустой поток - `Pending`;
  принятый байт будит поток, таймер - нет; после loopback вывод в serial работает.
  Байты эмулируются `common::send_from_terminal`. UART поднимает прерывание не
  на каждый байт, а когда FIFO наполнится или после паузы, поэтому тест ждёт
  байты в цикле с `hlt`.
- `tty_input.rs`: `tty::keys()` отдаёт разобранные клавиши с клавиатуры (буквы,
  стрелки, Ctrl + буква) и из терминала (Enter, стрелки, Backspace, Ctrl + C,
  UTF-8) в одном потоке; порядок внутри одного источника сохраняется; без ввода
  поток - `Pending`.
- `paging.rs`: ручная трансляция адресов `paging::translate_addr` (VGA-буфер
  отображён один к одному, смещение внутри страницы сохраняется, нулевая страница
  не отображена, результат совпадает с `OffsetPageTable`); область
  `physical_memory_offset` отображена на физическую память; настоящий
  `BootInfoFrameAllocator` выдаёт разные выровненные фреймы из `Usable`-регионов;
  `create_example_mapping` создаёт рабочее отображение страницы на VGA-буфер.
  Точка входа объявлена через `entry_point!`, чтобы получить `BootInfo`.
- `heap_allocation.rs`: после `init_heap` работают `Box`, `Vec`, `Rc` и `String`;
  память выделяется внутри кучи, освобождённая память переиспользуется (в сумме
  выделяется больше `HEAP_SIZE`), в том числе пока жива другая аллокация (с
  bump-аллокатором этот тест падает); блоки разных размеров не перекрываются;
  слишком большая аллокация через `try_reserve`
  возвращает ошибку, и куча продолжает работать; отображены ровно страницы кучи.
- `async_task.rs`: `SimpleExecutor` выполняет задачи до конца и возвращается,
  `await` возвращает значение, задачи выполняются в порядке `spawn`, задача,
  вернувшая `Pending`, опрашивается снова, задачи чередуются на `yield_now`,
  задача владеет перемещёнными в неё данными.
- `executor.rs` (`harness = false`): `Executor::run` никогда не возвращается,
  поэтому QEMU завершает последняя задача. Проверяется, что задачи, уступающие
  очередь, доходят до конца, а задачу, которая ждёт `keyboard::scancodes()`, будит
  прерывание клавиатуры, пока executor спит в `hlt`. Если задачу никто не
  разбудит, тест упадёт по `test-timeout`.
- `heap_oom.rs` (`harness = false`): аллокация больше кучи паникует с сообщением
  `memory allocation of N bytes failed`.
- `double_fault.rs` (`harness = false`): деление на ноль (divide error без
  обработчика) приводит к вызову обработчика double fault ядра. Page fault для
  этого больше не подходит: у него есть свой обработчик.
- `stack_overflow.rs` (`harness = false`): при переполнении стека обработчик
  double fault выполняется на отдельном стеке из IST. Без IST будет triple fault.
- `should_panic.rs`: паника корректно перехватывается, а `assert_eq!` действительно
  паникует.

### Тесты на панику

Раннер останавливается на первой панике, поэтому в одном образе может быть только
**один** тест, который обязан паниковать. Такой тест оформляется отдельным файлом
без раннера:

```toml
# Cargo.toml
[[test]]
name = "should_panic"
harness = false
```

`_start` вызывает тестируемую функцию напрямую. Если она вернулась, тест упал
(`Failed`). Если сработал `panic_handler`, тест прошёл (`Success`).

Если важно, **какая** именно паника произошла (например, паника обработчика
double fault, а не любая другая), `panic_handler` проверяет сообщение через
`common::panic_message_starts_with` из `tests/common/mod.rs` (подключается
строкой `mod common;`). Файлы в подпапках `tests/` cargo не считает отдельными
тестами, поэтому туда кладётся общий код интеграционных тестов. Там же
`common::init_heap` (инициализация кучи для тестов, которым нужен `alloc`),
`common::yield_now` (future, который один раз уступает очередь другим задачам) и
эмуляция ввода (нужны `rustos::init()` и включённые прерывания):

- `common::press_key(scancode)`: команда `0xD2` контроллера PS/2 кладёт скан-код
  в его выходной буфер и поднимает IRQ1, как настоящая клавиатура;
- `common::send_from_terminal(bytes)`: UART в режиме loopback принимает
  собственные отправленные байты, и они вызывают IRQ4, как байты из терминала.
  За раз - не больше `SERIAL_CHUNK` (16) байтов: столько вмещает приёмный FIFO,
  а пока идёт отправка, прерывания выключены и обработчик байты не забирает.

## Правила написания тестов

1. **Не полагаться на состояние экрана.** Unit-тесты делят один `WRITER` и
   выполняются в одном образе. Тест, который проверяет содержимое VGA-буфера, должен:
   - взять `WRITER.lock()` **один раз** и держать блокировку до конца проверки;
   - начинать вывод с `\n`, чтобы работать с чистой последней строкой.

   Дополнительно такой код оборачивается в
   `x86_64::instructions::interrupts::without_interrupts`: если обработчик
   прерывания, который печатает через `println!` (breakpoint, page fault),
   сработает, пока тест держит `WRITER`, он будет ждать этот lock вечно (deadlock).
   Обработчик может и вклиниться в вывод теста.
2. **Для сравнения строк на экране использовать `assert_row_eq`**
   (`src/drivers/vga/tests.rs`). Функция проверяет строку целиком, включая пробелы
   после текста, и в сообщении об ошибке указывает строку и колонку.
3. **Один тест проверяет одно поведение**, а имя говорит, что именно
   (`test_long_line_wraps`, а не `test_vga_2`).
4. **Код, который меняет состояние CPU или памяти** (загрузка IDT/GDT, включение
   прерываний, работа с таблицами страниц, аллокатор), тестируется в отдельном
   файле в `tests/`, а не в unit-тестах.
5. **Новая подсистема приходит вместе с тестами.** Минимум: unit-тесты модуля и
   проверка в `basic_boot.rs` (или отдельном интеграционном тесте), что подсистема
   инициализируется при загрузке.

## CI

Workflow `.github/workflows/build.yml` состоит из двух джоб:

- `test` ставит QEMU и запускает `make test` при каждом пуше в `master` и `dev`
  и на каждый PR в `master`;
- `release` запускается только при пуше в `master` и только если `test` прошёл
  (`needs: test`): собирает debug- и release-образы и публикует их в GitHub Releases.

Тесты на `dev` и в PR ловят ошибки до мерджа. Если тест упал на `master`,
релиз не создаётся.
