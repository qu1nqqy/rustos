# Тестирование rustos

Ядро работает без стандартной библиотеки (`no_std`), поэтому встроенный тестовый
фреймворк Rust (крейт `test`) недоступен. Тесты собираются в отдельные загрузочные
образы и запускаются внутри QEMU; результат передаётся наружу через код выхода
QEMU и последовательный порт.

## Как запустить

```sh
make test                      # все тесты (то же, что cargo test)
cargo test --lib               # только unit-тесты из src/
cargo test --test basic_boot   # один интеграционный тест
```

Нужны `bootimage` (`cargo install bootimage`) и `qemu-system-x86_64` в `PATH`.

## Как это устроено

```
cargo test ──► сборка тестового образа ──► bootimage runner ──► QEMU
                                                                  │
      serial (COM1, 0x3F8) ──► stdout терминала ◄─────────────────┤
      isa-debug-exit (порт 0xF4) ──► код выхода QEMU ◄────────────┘
```

- **Кастомный тест-раннер.** `#![feature(custom_test_frameworks)]` собирает все
  функции с атрибутом `#[test_case]` и передаёт их в `rustos::test_runner`
  (`src/lib.rs`). Раннер выполняет их по очереди и печатает `имя...\t[ok]`.
- **Вывод.** Тесты пишут в последовательный порт (`serial_print!` / `serial_println!`),
  QEMU перенаправляет его в stdout (`-serial stdio`). VGA-вывод (`println!`) в
  тестах тоже работает, но его не видно, потому что окно QEMU отключено (`-display none`).
- **Результат.** Раннер записывает `QemuExitCode` в порт `0xF4` устройства
  `isa-debug-exit`. QEMU завершается с кодом `(value << 1) | 1`:
  - `Success = 0x10` → код 33, который указан в `test-success-exit-code`, bootimage считает это успехом;
  - `Failed = 0x11` → код 35, тест считается упавшим.
- **Паника.** В тестовой сборке `#[panic_handler]` вызывает
  `test_panic_handler`: печатает `[failed]` с сообщением паники и выходит с `Failed`.
  Поэтому любой упавший `assert!` роняет весь тестовый образ: тесты после
  него уже не выполняются.
- **Зависание.** Если тест завис (например, из-за deadlock), bootimage убьёт QEMU
  через `test-timeout = 300` секунд и засчитает провал.

Настройки QEMU для тестов лежат в `[package.metadata.bootimage]` в `Cargo.toml`.

## Виды тестов

| Вид | Где лежит | Когда использовать |
|---|---|---|
| Unit-тесты | `src/<модуль>/tests.rs` | Проверка отдельного модуля, в том числе его приватных полей и функций |
| Интеграционные | `tests/<имя>.rs` с тест-раннером | Проверка поведения в «чистом» окружении: отдельный образ, собственный `_start` |
| Тесты на панику | `tests/<имя>.rs` с `harness = false` | Проверка того, что код **должен** паниковать |

### Unit-тесты (`src/<модуль>/tests.rs`)

Тесты не смешиваются с кодом: у каждого модуля они лежат в отдельном файле.

```
src/
├── lib.rs            ← в конце: #[cfg(test)] mod tests;
├── tests.rs          ← тесты lib.rs
├── vga_buffer.rs     ← в конце: #[cfg(test)] mod tests;
├── vga_buffer/
│   └── tests.rs      ← тесты vga_buffer
├── serial.rs
└── serial/
    └── tests.rs
```

`tests` — дочерний модуль тестируемого модуля, поэтому через `use super::*;`
ему доступны **приватные** типы, поля и функции (например, `ColorCode(0x1e)` или
`writer.column_position`). Из `tests/` их было бы не видно. Благодаря
`#[cfg(test)]` файл компилируется только при `cargo test` и в образ ядра не попадает.

Строку `mod tests;` ставим **в конец** файла модуля, после объявлений
`macro_rules!`: макросы (`println!`, `serial_println!`) видны только в коде,
который идёт после их определения.

Чтобы покрыть тестами новый модуль `foo`:

1. добавить в конец `src/foo.rs` строки `#[cfg(test)]` и `mod tests;`;
2. создать `src/foo/tests.rs`, начинающийся с `use super::*;`;
3. писать тесты с атрибутом `#[test_case]`.

Все unit-тесты библиотеки собираются в один образ, поэтому у них общее
глобальное состояние (`WRITER`, `SERIAL1`).

Сейчас покрыто:

- `vga_buffer`: кодирование цвета, раскладка структур в памяти (должна совпадать
  с текстовым VGA-буфером), вывод строки, перенос длинной строки, сброс колонки
  после `\n`, прокрутка экрана, замена не-ASCII байтов на `■` (`0xfe`), цвет
  записанных символов, «стресс» из 200 строк;
- `serial`: вывод через последовательный порт с форматированием;
- `lib`: соответствие `QemuExitCode::Success` значению `test-success-exit-code`;
- `interrupts`: в IDT зарегистрированы обработчики breakpoint, double fault,
  таймера и клавиатуры, у остальных исключений обработчиков пока нет; смещения
  PIC идут сразу после 32 исключений CPU, а `InterruptIndex` совпадает с линиями IRQ;
- `gdt`: в TSS задан стек для double fault (IST), остальные записи IST пустые;
  раскладка GDT (код ядра, TSS) и уровень привилегий селекторов (ring 0).

Таблицы IDT, GDT и TSS в unit-тестах только строятся, но не загружаются в CPU
(см. правило 4). По той же причине тестовый `_start` в `src/lib.rs` **не**
вызывает `rustos::init()`: в unit-тестах прерывания выключены.

### Интеграционные тесты (`tests/`)

Каждый файл собирается в **отдельный** загрузочный образ со своим `_start`. Это
позволяет проверить, что код работает сразу после загрузки, без инициализации
из `main.rs`, и изолировать тесты, которые меняют глобальное состояние CPU
(прерывания, GDT, таблицы страниц и т.д.).

- `basic_boot.rs`: VGA- и serial-вывод доступны сразу после загрузки.
- `interrupts.rs`: после `rustos::init()` (загрузка GDT, TSS и IDT) исключение breakpoint
  (`int3`) обрабатывается, в том числе многократно, и выполнение продолжается;
  загружена GDT ядра, а `CS` указывает на сегмент кода ядра; прерывания включены,
  прерывания таймера приходят, а `println!` не попадает в deadlock с обработчиком
  таймера.
- `keyboard.rs`: обработчик клавиатуры печатает нажатую клавишу, игнорирует
  отпускание, учитывает Shift. Нажатия эмулируются командой `0xD2` контроллера
  PS/2: она кладёт скан-код в его выходной буфер и поднимает IRQ1, как настоящая
  клавиатура. Результат тест читает прямо из VGA-памяти (`0xb8000`), отбрасывая
  точки от обработчика таймера.
  Если обработчик не сработает, CPU уйдёт в triple fault, и тест упадёт
  (QEMU запускается с `-no-reboot`).
- `double_fault.rs` (`harness = false`): page fault без обработчика приводит к
  вызову обработчика double fault ядра.
- `stack_overflow.rs` (`harness = false`): при переполнении стека обработчик
  double fault выполняется на отдельном стеке из IST. Без IST будет triple fault.
- `should_panic.rs`: паника корректно перехватывается, а `assert_eq!` действительно
  паникует.

### Тесты на панику

Раннер останавливается на первой панике, поэтому в одном образе может быть только
**один** тест, который обязан паниковать. Такой тест оформляется отдельным файлом
без раннера:

```toml
# Cargo.toml
[[test]]
name = "should_panic"
harness = false
```

`_start` вызывает тестируемую функцию напрямую. Если она вернулась, тест упал
(`Failed`). Если сработал `panic_handler`, тест прошёл (`Success`).

Если важно, **какая** именно паника произошла (например, паника обработчика
double fault, а не любая другая), `panic_handler` проверяет сообщение через
`common::panic_message_starts_with` из `tests/common/mod.rs` (подключается
строкой `mod common;`). Файлы в подпапках `tests/` cargo не считает отдельными
тестами, поэтому туда кладётся общий код интеграционных тестов.

## Правила написания тестов

1. **Не полагаться на состояние экрана.** Unit-тесты делят один `WRITER` и
   выполняются в одном образе. Тест, который проверяет содержимое VGA-буфера, должен:
   - взять `WRITER.lock()` **один раз** и держать блокировку до конца проверки;
   - начинать вывод с `\n`, чтобы работать с чистой последней строкой.

   Дополнительно такой код оборачивается в
   `x86_64::instructions::interrupts::without_interrupts`: обработчик таймера
   печатает `.`, и если он сработает, пока тест держит `WRITER`, то будет ждать
   этот lock вечно (deadlock). Обработчик может и вклиниться в вывод теста.
   В интеграционных тестах с `rustos::init()` таймер тоже печатает `.`, поэтому
   проверка экрана должна их пропускать (см. `tests/keyboard.rs`).
2. **Для сравнения строк на экране использовать `assert_row_eq`**
   (`src/vga_buffer/tests.rs`). Функция проверяет строку целиком, включая пробелы
   после текста, и в сообщении об ошибке указывает строку и колонку.
3. **Один тест проверяет одно поведение**, а имя говорит, что именно
   (`test_long_line_wraps`, а не `test_vga_2`).
4. **Код, который меняет состояние CPU или памяти** (загрузка IDT/GDT, включение
   прерываний, работа с таблицами страниц, аллокатор), тестируется в отдельном
   файле в `tests/`, а не в unit-тестах.
5. **Новая подсистема приходит вместе с тестами.** Минимум: unit-тесты модуля и
   проверка в `basic_boot.rs` (или отдельном интеграционном тесте), что подсистема
   инициализируется при загрузке.

## CI

Workflow `.github/workflows/build.yml` состоит из двух джоб:

- `test` ставит QEMU и запускает `make test` при каждом пуше в `master` и `dev`
  и на каждый PR в `master`;
- `release` запускается только при пуше в `master` и только если `test` прошёл
  (`needs: test`): собирает debug- и release-образы и публикует их в GitHub Releases.

Тесты на `dev` и в PR ловят ошибки до мерджа. Если тест упал на `master`,
релиз не создаётся.
